Android SDK (LAB Guard)

프로젝트 개요

  • 고객사 앱 내에 워터마크, 카메라, 보안 문서 뷰어 등 다양한 기능을 SDK 형태로 제공
  • 기능 제안부터 개발, 배포, 가이드 문서, 현장 기술 지원까지 전 과정 주도

1 — 가시성 워터마크

가시성 워터마크(Visible Watermark) 기능 개발

목적 / 역할

  • 고객사 앱 화면에 사용자 정보·시간을 워터마크로 표시하여 화면 유출 시 유출자 특정 가능
  • 기능 아이디어를 직접 제안하고 MVP 개발부터 대기업 그룹사 도입까지 전 과정 주도

구현 내용

  • Canvas + View 기반 렌더링: 전체 화면·구역 분할 워터마크, 화면 방향 전환 완전 대응
  • 시간 단위 자동 갱신, 커스터마이징 가능한 텍스트/스타일/위치 옵션
  • LayerEmbedder를 통해 고객사 앱의 기존 View 구조에 비침투적으로 삽입

성과

  • 대기업 그룹사 전체 도입 → Android 기준 매출 3억원 이상 기여
  • 자체 제안 아이디어에서 시작한 기능이 사내 주요 매출원으로 정착

트러블슈팅

TROUBLE · 01

크로스 플랫폼 환경 지원 부재

ProblemSDK가 Native 환경만 지원하여 Flutter, React Native, Cordova 기반 고객사 니즈를 충족하지 못함
Cause멀티플랫폼 환경 검증 및 연동 가이드 부재
SolutionMVP를 빠르게 개발하여 크로스 플랫폼 연동 가능성을 검증하고, 현장 기술 지원까지 직접 제공
Result실제 계약 성립으로 이어져 신규 매출 창출 및 고객사 신뢰 확보

2 — 카메라 모듈

Camera2 API 기반 프레임 검출 모듈 개발

구현 내용

  • CaptureRequest 세부 제어: 노출, ISO, 화이트밸런스, AF 모드 등 파라미터 직접 제어로 검출 알고리즘 최적화
  • Lifecycle 자동 관리: Activity Lifecycle을 주입받아 카메라 세션 생성·해제 자동화 → 클라이언트 코드 부담 최소화 및 리소스 누수 방지

트러블슈팅

TROUBLE · 01

Camera Lifecycle 관리 미비로 인한 Crash

Problem고객사가 App Lifecycle에 따라 Camera를 제어하는 과정에서 빈번한 Crash 발생
Cause다양한 앱 환경에 따른 Camera On/Off 수동 관리의 복잡성
SolutionLifecycle을 SDK가 주입받아 동적 관리하도록 구조 개선, 수동 제어 옵션도 함께 제공
ResultCrash 발생 감소, 다양한 환경에서 안정적 카메라 동작 확보

3 — 보안 문서 뷰어

보안 문서 뷰어 개발 (PDF · Word · Excel · PPT)

구현 내용

  • PDF 뷰어: 네이티브 PdfRenderer로 페이지 비트맵 렌더링, 핀치 줌·지연 렌더링(Lazy Rendering) 적용
  • 오피스 문서 뷰어: OOXML(.docx .xlsx .pptx)을 XML 직접 파싱 → HTML 변환 → WebView 렌더링. 표·이미지·차트·병합 셀 등 주요 서식 지원
  • 보안 제어: FLAG_SECURE로 스크린샷·화면 녹화 차단 / Android 13+ 앱 전환 썸네일 보안 처리 / 클립보드 변경 감지

4 — 모듈 아키텍처

Reflection 기반 모듈 간 연동 아키텍처 설계

문제 정의

  • Detect·Embed·Protect 등 각 SDK를 독립 AAR로 배포하는 구조상, 고객사가 일부 모듈만 선택 도입해도 컴파일 오류 없이 동작해야 함

SDK 생태계 계층 구조

접근 방식 및 구현

  • 컴파일 타임 직접 의존 없이 런타임에 동적으로 모듈을 탐지·호출하는 Reflection 기반 연동 구조 채택
  • 선택적 모듈 구성, 독립적 버전 관리, ProGuard 난독화 환경에서의 안정적 동작 동시 충족

기술적 고민과 의사결정

  • Reflection은 타입 안전성이 없고 IDE 지원 불가 → 유지보수 비용이 높다는 트레이드오프 존재
  • 단, 독립 배포 모듈 간 선택적 결합이라는 구조적 제약 하에서는 합리적인 선택으로 판단
  • 장기적으로는 인터페이스(공통 추상화 레이어)로 정의 후 직접 참조로 전환하는 방향을 개선안으로 제시

5 — API 설계

SDK 상태 피드백 API 설계 및 통합 가이드 문서 제작

문제 정의

  • SDK 적용 후 성공/실패 여부 및 실패 원인을 확인할 수 없어 고객사 기술 문의가 빈번하게 발생

구현 내용

  • 초기화·권한·네트워크·인증 등 각 단계 결과를 completion / exception 콜백 + Enum 상태로 세분화하여 전달
  • 단순 에러 코드가 아닌, 예상 원인과 조치 방향을 포함한 상태 분류 체계로 설계 → 자가 진단 가능
  • 통합 가이드 문서 제작으로 고객사 온보딩 시간 단축

성과

  • 고객사 기술 문의 90% 이상 감소 — 고객사 개발 효율 및 기술 지원 효율 향상

크로스플랫폼 MVP 개발 및 현장 기술 지원

  • React Native, Flutter, Cordova 환경 연동 가능성 검증 및 현장 방문 기술 지원

성과

  • Socket.IO 자동화 테스트 환경: 좌표계, 온도, 배터리, 메모리, FPS 실시간 수집·분석
  • Admin/User 플레이버 분리: 원격 제어·측정 가능한 구조로 재현 가능한 실험 환경 확보
  • 인식률 계산식 정의: 절대적/상대적 인식률 구분 → 디바이스별·환경별 비교 기준 수립

트러블슈팅

TROUBLE · 01

FPS 변동으로 인한 인식률 편차 문제

Problem조도나 모션 상황에 따라 FPS가 자동으로 변동하여 인식률 편차 발생
CauseCamera2 API의 자동 FPS 설정이 어두운 환경에서 셔터를 오래 열어야 하므로 FPS를 강제로 낮추는 구조적 특성
SolutionFlash 기능 사용 시 안정적으로 높은 FPS 확보 가능함을 검증 / 강제 FPS 고정 설정을 통한 인식률 개선 실험 수행
ResultFPS 제어가 인식률 개선에 유의미한 영향을 미친다는 결론 도출 → SDK 최적화 방향성 제시

TROUBLE · 02

데이터 수집 과정의 반복성 / 정밀도 부족

Problem초기 실험 환경(디바이스 위치, 각도)으로 인해 데이터의 신뢰도가 보장되지 않음
Cause수동 측정 방식의 한계
Solution앱 내에 좌표계, 수평계, 결과 자동 송출 기능을 추가하여 테스트 환경 표준화 및 자동화
Result반복 측정 시에도 일관된 데이터 확보 및 신뢰도 향상

TROUBLE · 03

인식률 정의의 모호성

Problem단순 성공/실패만으로 인식률을 평가하여 환경 차이에 따른 세부 분석이 어려움
Solution절대적/상대적 인식률을 구분하는 계산식 정의 (1만 회 프레임 총 시간, 성공 인식 횟수, FPS 종합 검토)
Result디바이스별, 환경별 비교 가능한 체계적 성능 평가 기준 확립
